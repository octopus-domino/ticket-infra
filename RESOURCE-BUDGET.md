# Сервер 2 CPU / 4 ГБ RAM

Рабочий профиль: `compose.api.yml` + `compose.postgres.yml`.

| Сервис | Предел памяти |
|---|---:|
| Java, nginx, supervisor, нативный OCR и временный маршрутизатор вместе | 1792 MiB |
| PostgreSQL | 512 MiB |
| Tyk | 384 MiB |
| Redis | 160 MiB |
| Всего контейнеры | 2848 MiB |

Остаётся около 1,2 GiB для ОС, Docker и файлового кеша. Сторонние сервисы,
включая отдельный draw.io, должны помещаться в этот остаток; проверьте `docker stats`.
На действующем сервере Draw.io ограничен 512 MiB, его Java heap — 256 MiB.
Вместе с ним пределы контейнеров составляют 3360 MiB, оставляя около 550 MiB
для ОС и Docker на машине с 3915 MiB RAM. При пересоздании Draw.io сохраняйте
этот лимит памяти и heap; нельзя оставлять ему прежний предел 1 GiB.
Java heap ограничен 1024 MiB, direct buffers — 128 MiB; оставшаяся память контейнера
нужна потокам, metaspace, шрифтам, изображениям и Tesseract. OCR и экспорт используют
общий слот: одновременно выполняется только одна тяжёлая операция. Остальные сразу
получают HTTP 429, без очереди тяжёлых заданий. Число OpenMP-потоков — один.

PostgreSQL: shared_buffers=128MB, work_mem=2MB, hash_mem_multiplier=1,
maintenance_work_mem=32MB, autovacuum_work_mem=16MB, один autovacuum worker,
20 соединений максимум, пул приложения — пять. Параллельные запросы и JIT отключены.
effective_cache_size — оценка кеша для планировщика, а не выделение памяти.
fsync и synchronous_commit остаются включены. Не увеличивайте пул без пересчёта памяти.

Фоновая генерация: один worker, два места в очереди, до 32 MiB результата пачки.
Генерация и упаковка используют тот же слот, что OCR и экспорт. При занятом слоте
операция отклоняется: автоматическое ожидание и бесконечные повторы не включены.
nginx допускает один одновременный тяжёлый HTTP-запрос, чтобы несколько больших
JSON-тел не заняли heap ещё до проверки семафора. Обычные GET-запросы, включая
опрос статуса фонового задания, этим ограничением не затрагиваются.

## Сборка и обновление

Сборка **по умолчанию выполняется на этом же сервере**, с остановкой CoDoc.
Отдельная машина или CI не требуются. Нужны Docker Buildx, Compose v2, Bash,
`flock` из util-linux и место для кешей, образов и резервных копий (ориентир —
не менее 8 ГБ свободного места плюс размер данных).

| Этап | Ограничение |
|---|---:|
| Весь контейнер BuildKit, включая исполняемые шаги | 2304 MiB, 2 CPU |
| Одновременно выполняемых шагов BuildKit | 1 |
| Node heap каждого процесса | 768 MiB |
| Vitest | 1 worker |
| Maven heap | 384 MiB |
| Тестовая JVM Maven | 768 MiB, один fork |
| JVM создания схемы перед миграцией | 512 MiB heap |
| Контейнер переноса H2 → PostgreSQL | 768 MiB, heap 512 MiB |

Bash-entrypoints используют `scripts/lib/low-memory-build.sh`; `build.ps1` задаёт
тот же ограниченный Buildx worker нативно, без требования установить GNU flock на Windows.
Лимит задан
именно контейнеру отдельного Buildx builder, поскольку лимит Compose не ограничивает
сборку. Builder использует `max-parallelism=1`, проверяются фактически установленные
лимиты Docker. Перед стартом требуется не менее 2816 MiB `MemAvailable`.
Если память занята другими сервисами, скрипт завершится до сборки и вернёт прежние
контейнеры; чужие сервисы автоматически не останавливаются.

Во время сборки остановлены приложение, PostgreSQL, Tyk и Redis этой установки.
Сборщик останавливается до запуска PostgreSQL/Java. Рабочая фаза и сборка не складываются
по памяти. Swap не требуется для расчётного бюджета: builder ограничен 2304 MiB
RAM и таким же общим лимитом RAM+swap. Существующий swap скрипты не меняют.

Кеши npm, Maven и Docker-слоёв сохраняются в выделенном builder `codoc-lowmem-v1`.
Повторная сборка использует кеш; `--no-cache` по умолчанию не включён.
Проверки и тесты остаются включены. В Docker-сборке выключены frontend sourcemaps;
при обычной разработке это поведение не меняется.

Из общей папки трёх репозиториев:

```bash
# Однократный переезд из H2: резервная копия → сборка → перенос → запуск.
bash ticket-infra/scripts/migrate-postgres.sh --migrate
# Последующие обновления PostgreSQL, с резервной копией и остановкой на сборку.
./ticket-infra/deploy.sh
# Обновление прежней H2-установки без переезда.
bash ticket-infra/deploy.sh
# Только собрать образ: скрипт остановит и затем вернёт прежние контейнеры.
bash ticket-infra/build.sh
```

При ошибке сборки до изменения БД прежние контейнеры запускаются снова.
После начала импорта или изменения схемы автоматический запуск старого приложения
запрещён: оно остаётся остановленным, путь к резервной копии выводится в сообщении.
Это позволяет избежать записи в две базы. SIGINT/SIGTERM проходят через тот же cleanup;
SIGKILL и отключение питания обработать программным trap невозможно.

Для необязательного использования уже готовых образов сохранён
`CODOC_BUILD_ON_HOST=false`; штатное значение — `true`.
Не используйте прямой `docker compose build` или `up --build` на этой VM:
они обходят общий механизм ограничений и остановки сервисов.

Основание настройки: [Docker container driver — лимиты памяти и CPU](https://docs.docker.com/build/builders/drivers/docker-container/),
[BuildKit — ограничение параллелизма](https://docs.docker.com/build/buildkit/configure/).

## Проверка на сервере

После запуска проверьте `docker stats --no-stream`, `free -m`,
`docker inspect --format '{{.State.OOMKilled}}' <container>` и системный журнал OOM.
Нагрузочный прогон: повторные OCR, параллельный экспорт, обычные запросы и импорт
Excel одновременно. При перегрузке тяжёлые запросы должны получать 429, сайт и
база оставаться доступны. Проверяйте также рост диска временными файлами и логами.
Ограничения уменьшают риск OOM, но не гарантируют работу документов любого размера.
Нативный OCR и полный состав production-сервисов требуют проверки на целевой машине.

Справочники: [PostgreSQL 17: память](https://www.postgresql.org/docs/17/runtime-config-resource.html),
[Docker Compose: ограничения сервисов](https://docs.docker.com/reference/compose-file/services/).
