# Клиентское API, Tyk и российские источники

Добавлен самостоятельный Tyk Gateway + Redis без Dashboard, MongoDB и платных компонентов. Выпуск, просмотр метаданных и отзыв ключей находятся в CoDoc: `/app/api-access`. Схема API: `ticket-editor/public/client-api.openapi.json`. Запуск контейнеров в этой среде не проверен: Docker daemon недоступен.

## Развёртывание

1. Скопировать `api.env.example` в `.env`. Задать независимые случайные секреты длиной не менее 32 символов. `APP_SECRETS_ENCRYPTION_KEY` хранить вместе с резервной копией БД: без него нельзя расшифровать credentials источников и удалить ключи из Tyk. В Git `.env` не попадает.
2. Проверить `docker compose --env-file .env -f compose.api.yml config --quiet`.
3. Существующую БД сначала скопировать вместе с `data/generation`. Оставить `DB_SCHEMA_MODE=validate`: миграции расширяют схему. Только для новой пустой БД первый запуск требует `DB_SCHEMA_MODE=update`; затем вернуть `validate`.
4. Из `ticket-infra` выполнить `bash build.sh`, затем `docker compose --env-file .env -f compose.api.yml up -d --no-build`. Сборка останавливает CoDoc и ограничена 2304 MiB / 2 CPU; см. `RESOURCE-BUDGET.md`. Это отдельный compose, не дополнение к другому файлу.
5. На внешнем reverse proxy настроить HTTPS: веб-приложение → `127.0.0.1:8090`, `/client-api/` → `127.0.0.1:8088`. Сохранить путь `/client-api/`. Порт управления Tyk 8081 и Redis наружу не публикуются.
6. Открыть CoDoc, войти обычным пользователем, создать ключ. Скопировать значение сразу: повторно показываются только название, префикс, срок, права и счётчики. Проверить запрос ключом, отзыв и повторный отказ в доступе.

План памяти контейнеров: приложение 2304 МБ (Java heap 1536 МБ), Tyk 384 МБ, Redis 160 МБ. Это лимиты конфигурации, а не результат нагрузочного измерения. На 2 CPU / 4 ГБ OCR выполняется по одному запросу; Ollama выключена. Сборка образа может потребовать больше памяти, чем работа готовых контейнеров: предпочтительно собирать отдельно. Параллельный OCR, тяжёлые PDF и тысячи моделей требуют замера RSS, CPU и задержек на реальных документах.

## Права и квоты

- `read`: собственные схемы, модели, шаблоны, статус и скачивание известного задания.
- `generate`: синхронная/асинхронная генерация и предпросмотр.
- `data:write`: изменение собственных схем, моделей и шаблонов.
- Ключи не дают доступ к регистрации, управлению ключами, источниками, общими библиотеками или правами пользователей. Для этого нужен пользовательский вход.
- Приложение самостоятельно проверяет владельца, срок, отзыв, хеш ключа и права. Заголовок с чужим user ID не используется для авторизации.
- Лимит приложения: 60 запросов/минуту и 10 000 за календарный месяц UTC на ключ. У Tyk месячная квота является скользящим периодом 30 дней; срабатывает более строгое ограничение. Есть также общие лимиты генерации и шлюза. Несколько ключей не превращают VM в неограниченный генератор.
- При недоступном Tyk выпуск нового ключа не завершается. При отзыве приложение блокирует ключ первым; незавершённую очистку шлюза можно повторить в интерфейсе. Резервировать надо БД, каталог генераций и Redis volume.

Проверка через shell (ключ брать из защищённого окружения, не вставлять в репозиторий):

```powershell
curl.exe --fail-with-body -H "X-API-Key: $env:CODOC_API_KEY" https://api.example/client-api/templates
```

## 1С → CoDoc: клиентское API

`examples/one-c-generation.bsl` показывает HTTPS-запрос из 1С с отдельным ключом и сохранение бинарного ответа. Параметры сервера, ID шаблона и ключ задаются вызывающим кодом. Пример не исполнялся в платформе 1С: здесь нет её runtime. Нужна приёмка на используемой версии платформы и конфигурации. Большие партии отправлять POST-запросом в `/client-api/generate`, опрашивать `/client-api/generate/{jobId}`, скачивать `/client-api/generate/{jobId}/result`; не запускать длинную генерацию в UI-потоке 1С.

## CoDoc ← 1С / Битрикс24 / amoCRM

Экран `/app/integrations`: источник → предпросмотр → схема → сопоставление → исправление строки → импорт. В 1С можно использовать опубликованный OData JSON (`.../odata/standard.odata/Catalog_...?%24format=json`) или собственный HTTP-сервис. Набор коллекций и права определяются конфигурацией 1С. Выбирать стабильный `Ref_Key`, а не представление/номер строки.

Для Битрикс24 поддерживается JSON-результат webhook/REST endpoint, для amoCRM — JSON `_embedded`. URL webhook часто содержит секрет: он шифруется целиком и не возвращается браузеру. Поддерживаются Basic, Bearer и URL с уже выданным webhook. OAuth consent/refresh и доступ ко всем конфигурациям CRM не заявлены. Использовать отдельную учётную запись источника с минимальными правами.

Администратор задаёт `CONNECTOR_ALLOWED_ORIGINS`, например `https://onec.example:8443,https://company.bitrix24.ru`. Это точные origin, без `*` и путей. Redirect не выполняется. Произвольные хосты, userinfo, fragment, link-local/multicast адреса блокируются. Внутренний сервер допускается только явно разрешённым origin. Тело JSON до 8 МБ, до 10 000 записей, предпросмотр живёт 5 минут; одновременно до 8 кэшированных наборов. Секреты не журналируются.

Повторный импорт обновляет собственную модель по паре schema ID + внешний ID внутри подключения; одинаковые имена не используются как ключ. Все строки проверяются до записи. Источник не удаляет отсутствующие записи. Автообновление 15/60/1440 минут повторяет сохранённое сопоставление, без разовых ручных исправлений. Если ответ содержит следующую страницу, показана только возвращённая страница и автообновление запрещено: настроить полный фильтрованный экспорт. Автоматический обход всей пагинации и двусторонняя запись в CRM не реализованы.

## История и библиотеки

`/app/history`: готовые файлы, исходные снимки и ошибки сохраняются семь дней. Скачивание возвращает тот же результат; повторяются только ошибочные позиции на сохранённом снимке. Старые задания до введения снимков используют актуальные исходники при повторе и помечаются в интерфейсе.

Версии документов/шаблонов: до 20 на ресурс, 30 дней и 50 МБ на владельца. Восстановление создаёт отдельную копию. Версии могут пережить удаление исходного документа до очистки по сроку. Это не резервная копия всей системы.

`/app/libraries`: серверные общие библиотеки, явное сохранение и загрузка между устройствами, папки, копии шаблонов, пользовательские штампы, стили, символы и фирменная палитра. До 10 библиотек на владельца, 500 элементов/10 МБ на библиотеку, 50 участников. Владелец выдаёт доступ уже зарегистрированному пользователю; editor меняет незащищённое, viewer читает и копирует. Только владелец меняет защиту. Защита папки распространяется на содержимое. Копирование не является DRM: имеющий чтение может сделать свою копию.

Сохранение использует номер версии и возвращает 409 при конфликте; перезагрузка явно отменяет несохранённые изменения. Локальные ресурсы автоматически не отправляются. Установка добавляет новые копии и не заменяет существующие. Для их использования надо заново открыть редактор. Совместное редактирование одного холста в реальном времени не реализовано.
