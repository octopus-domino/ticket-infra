# Сайты-конструкторы и короткие ссылки CoDoc

Одна кодовая база обслуживает готовые сценарии и сайты из конструктора:

- `invite.codoc.site`: приглашение → публичная страница → PDF → RSVP; имена гостей доступны только по секретной ссылке управления.
- `certificates.codoc.site`: имена → персональные PDF → QR → проверка записи о публикации. Проверка записи не удостоверяет полномочия выдавшей организации.
- `menu.codoc.site`: блюда и цены → PDF и QR → обновление меню без замены ссылки.
- `tickets`, `gifts`, `badges`, `passes`, `resume`, `schedule`, `greetings`: билеты, подарки, бейджи, пропуска, резюме, расписания и открытки.
- `proposals.codoc.site`: Excel → позиции/суммы → многостраничное КП → PDF и ссылка для клиента.
- `/solutions/`: каталог всех сценариев; входы доступны также с главной страницы.
- `/sites/new`: сценарий, заголовок, поля и оформление → публикация на выбранном `имя.codoc.site`.
- `go.codoc.site/Ab7kQ2mNx9Rt`: короткая ссылка. 12 равномерно случайных символов Base62 (~71 бит); ограничение уникальности в БД и повтор транзакции при коллизии. Адрес ведёт только на публикации CoDoc, произвольные URL не принимаются.

## Однократная настройка доменов

1. Добавьте DNS `A *.codoc.site → IP сервера`. Если используется IPv6, корректно настройте соответствующую AAAA-запись. Системные точные записи (`www`, `drawio`, почта) сохраняются.
2. Выпустите TLS-сертификат для `codoc.site` и `*.codoc.site` через DNS-01 с автоматическим продлением. HTTP-01 не подходит для wildcard.
3. Для Cloudflare подготовлен `scripts/configure-wildcard-cloudflare.sh`. Он требует `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ZONE_ID`, `CODOC_PUBLIC_IP`, `ACME_EMAIL` и установленный плагин certbot-dns-cloudflare. Скрипт не меняет существующую wildcard-запись, указывающую на другой сервер, и не выводит токен.
4. Подключите `nginx.journeys.conf` к внешнему nginx рядом с существующим конфигом основного сайта; проверьте пути сертификата и порт upstream. По умолчанию в примере 8090; для прежнего `ticket-app` и миграции, сохранившей порт, замените на 8080. Затем `nginx -t` и `systemctl reload nginx`.
5. Обновите приложение. Внутренний nginx должен направлять `/start`, `/s`, `/sites`, `/d`, `/manage`, `/issues` и корень поддоменов в SPA. API проксируется без изменения.
6. Для сканирования QR из закрытого реестра внешний nginx не должен запрещать камеру: если он выставляет `Permissions-Policy`, используйте `camera=(self)`. Запуск камеры требует HTTPS и действия пользователя; при отсутствии BarcodeDetector доступен ручной ввод кода.

После этой настройки создание сайта не вызывает DNS API: конструктор сохраняет конфигурацию, а приложение определяет сайт по имени хоста. Если wildcard ещё не готов, сайты можно проверять по `/s/имя` на основном домене.

## Управление

Секрет управления выдаётся только при создании и передаётся в URL-фрагменте, затем в заголовке `X-Management-Key`. В базе хранится SHA-256 хеш, в публичном ответе секрет отсутствует. Управляющую ссылку нужно сохранить; доступ по ней позволяет менять/отзывать публикацию. Отзыв отключает и страницу, и короткую ссылку, и PDF; ответы гостей удаляются.

API ограничивает частоту создания, обновления, ответов и рендера PDF. Batch сертификатов сохраняется атомарно. Идентификатор ответа гостя обеспечивает обновление его собственного RSVP вместо повторного добавления.

Выпуск `/issues/:id#key=…` объединяет получателей в закрытый реестр с общим ключом
управления и PDF всей пачки. Билеты и подарочные сертификаты погашаются транзакционно
один раз. Продление пропуска меняет срок по прежней ссылке, отзыв прекращает доступ.
Для сервера 2 CPU / 4 ГБ обязателен [ресурсный профиль](RESOURCE-BUDGET.md).

Новые сайты собираются настройками существующих сценариев. Новый тип серверного действия (например, платёж или новая внешняя интеграция) требует отдельной реализации и проверки.
