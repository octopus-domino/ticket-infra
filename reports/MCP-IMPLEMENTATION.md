# Техническая реализация MCP в CoDoc и приватном Journey

В коде четыре MCP-интеграции. OSM и Островок запускаются отдельными контейнерами в сети Compose `api`. Wikimedia Commons и PoemShip подключаются как внешние HTTP-источники. Браузер и приложение Journey обращаются к прикладному API и получают нормализованные результаты. Адреса источников и имена инструментов задаются серверной конфигурацией.

| Интеграция | Выполнение | Назначение | Инструменты |
|---|---|---|---|
| OSM | Локальный HTTP–stdio мост и пакет `osm-mcp` | Тематические POI, атрибуты объекта | `find_nearby_pois`, `poi_details` |
| Wikimedia Commons | Pipeworx, внешний Streamable HTTP | Фотографии с авторством и лицензией | `commons_wikimedia_search`, `file_info` |
| Островок | Собственный Python-сервис, локальный Streamable HTTP | Каталожные карточки отелей | `search_hotels` |
| PoemShip | Внешний HTTP MCP, специализированный Java-клиент | Справочник, поиск стихов, получение произведения | `library_guide`, `find_poems`, `get_poem` |

## Общий Java-транспорт

`McpClientFactory` создаёт синхронные клиенты MCP Java SDK с Jackson 2 и `HttpClientStreamableHttpTransport`. URI разбирается на origin и путь, по умолчанию `/mcp`. Допустимы HTTP и HTTPS с заданным host; query, fragment и userinfo отклоняются. HTTP-редиректы отключены. По умолчанию соединение и инициализация ограничены 3 секундами, запрос к инструменту — 15 секундами, ответ — 1 000 000 байт. Кеширование схем вызова выключено. Создание bean на старте приложения не вызывает внешний сервис.

OSM и Commons используют `McpToolSession`. Инициализация происходит при первом вызове. На один адаптер допускается один активный вызов через `Semaphore.tryAcquire()`. Результат берётся из `structuredContent` либо из текстового блока, который целиком разбирается как JSON. Допустимые инструменты зашиты отдельно для каждого адаптера. После сбоя установлен перерыв 60 секунд. В лог попадает имя группы инструментов. Аргументы и ответы остаются данными прикладного процесса. Островок использует тот же SDK и фабрику, с собственным управлением жизненным циклом и перерывом после ошибки.

## OpenStreetMap

Путь запроса: **Journey → API поиска мест → Java → OSM MCP или прикладной fallback**. Расчёт маршрута по дорогам живёт отдельно в `/api/journeys/routes/road` и выполняется через цепочку `RoadRouter`. Сопоставление GPS с пешеходным графом выполняется в Journey, описание доступно в `private_jorney/docs/recorded-walk-map-matching.md`.

- Сборочная цель `osm-mcp` в Dockerfile использует Node.js 24, npm lockfile с `osm-mcp@0.3.2` и отдельное Python-окружение с `mcp-proxy==0.15.0`. Мост слушает порт 8000 внутри контейнера. Он работает в stateless-режиме и запускает Node-программу через stdio. Допустимые HTTP Host указаны при запуске. Инициализация моста ограничена 20 секундами.
- `compose.walks.yml` добавляет сервис к проекту `codoc`. Хостовый порт отсутствует. Ограничения — 256 МиБ, 0,5 CPU и 64 процесса. Сняты capabilities, задан `no-new-privileges`. Healthcheck проверяет TCP-порт 8000. Сетевой адрес Java — `http://osm-mcp:8000/mcp`.
- При `find_nearby_pois` адаптер передаёт `near` в формате `lat,lon`, `category`, `radius_m` и `limit`. На вызов для одной категории выделяется до 25 результатов. Общая выборка дедуплицируется по OSM ID и ограничивается лимитом вызывающей стороны.
- `poi_details` принимает проверенный `osm_id` вида `node/123`, `way/123` или `relation/123`. Парсер проверяет координаты, ID, имя и длину полей, собирает OSM-теги из `tags`, текстовых полей, `category/categories` и `properties`, выдаёт `opening_hours` и Wikidata при наличии.
- Доступность MCP определяется через `OSM_MCP_ENABLED` и `OSM_MCP_URL`. При запуске через `deploy.sh` включение Compose-оверлея управляется `CODOC_WALK_MCP_ENABLED`. Поиск может использовать прикладные Overpass и Photon. Сервисы тематик и поиска по области распределяют время между источниками и отменяют оставшиеся задачи после ответа. Готовая геометрия маршрута сохраняется независимо от обогащения POI.

Код: `compose.walks.yml`, цель `osm-mcp` в `Dockerfile`, `ticket-pdf/.../mcp/NiCOsmMcpClient.java`, `OsmPoiSource.java`, `WalkThemeService.java`, `WalkAreaSearchService.java`.

## Wikimedia Commons

Путь запроса: **запрошенное обогащение остановок → PhotoEnricher → Pipeworx → Wikimedia Commons**. Включение через `COMMONS_MCP_ENABLED`, адрес через `COMMONS_MCP_URL`. По умолчанию используется `https://gateway.pipeworx.io/commons-wikimedia/mcp`.

1. `PipeworxCommonsMcpClient` очищает имя места от управляющих символов, кавычек и фигурных скобок. Добавляет фильтр `nearcoord:<radius>m,<lat>,<lon>`. Радиус зажат в диапазон 50–1000 м.
2. Поиск выполняется в namespace 6, возвращается до трёх кандидатов MCP. Принимаются заголовки `File:` длиной до 500 символов. Для каждого выполняется `file_info`, затем `CommonsImages` нормализует ссылки и лицензию.
3. При отсутствии результата или проблеме с MCP применяется прямой Commons API geosearch. Последний источник — фотография Wikimapia при наличии проверяемой лицензии и автора.
4. `PhotoEnricher` принимает до 12 остановок и выделяет до 18 секунд на обогащение. Кеш до 128 записей на 30 минут хранит найденные и пустые результаты. Скачать можно разрешённый JPEG или PNG размером до 900 000 байт, без редиректов.
5. Через `JourneyMediaService` изображение получает ID ресурса. Ответ связывает его с ID остановки и сохраняет ссылку на источник, автора и лицензию. Недоступное изображение оставляет остановку без фото.

Код: `PipeworxCommonsMcpClient.java`, `CommonsImages.java`, `PhotoEnricher.java`. Наличие фотографии, пригодной по лицензии, зависит от результата источников.

## Островок

Путь запроса: **CoDoc → API поиска отелей → TripHotelCatalog → собственный MCP → публичный каталог ostrovok.ru**.

### Контракт сервера

Python 3.12, только стандартная библиотека, `BaseHTTPRequestHandler` и однопоточный `HTTPServer`. Локальный запуск слушает `127.0.0.1:8192`. В контейнере используется `MCP_BIND=0.0.0.0` и `MCP_PORT=8192`. Compose публикует сервис в сети `api` без хостового порта. Healthcheck выполняет `GET /health` и ожидает HTTP 200. Этот запрос показывает, что процесс жив. Получение отелей проверяет реальный `tools/call`.

- `POST /mcp` принимает одиночное сообщение JSON-RPC 2.0 до 8192 байт. POST с заголовком `Origin` отклоняется. Тайм-аут входного сокета — 8 секунд.
- `initialize` возвращает MCP `2025-03-26`, имя `codoc-ostrovok`, версию `1.0` и возможность вызова tools. Запрос без `id` получает 202, `ping` — пустой результат, `tools/list` — одну схему. Неизвестный метод возвращает JSON-RPC `-32601`.
- `tools/call` с именем `search_hotels` принимает `city`, `checkIn`, `checkOut`, `guests`. Город до 120 символов, гости — целое 1–12, длительность между ISO-датами 1–90 ночей. Поддерживаются Москва, Санкт-Петербург, Казань и Сочи с русскими и английскими именами из таблицы `CITIES`.
- Успешный ответ содержит `structuredContent.catalogOnly=true` и `hotels[]`. При недоступном каталоге, неизвестном городе или некорректных полях вызов возвращает `isError=true` с кратким текстом. Внешние HTML и подробности исключений наружу не передаются.

### Получение и нормализация

Город преобразуется в фиксированный slug. Формируется HTTPS-запрос к `ostrovok.ru/hotel/russia/<slug>` с собственным User-Agent и тайм-аутом 6 секунд. Разрешён редирект на тот же host в пределах `/hotel/russia/`. Чтение ограничено 2 МБ. Из `script[type=application/ld+json]` читаются объекты `ItemList` и элементы типа `Hotel`. Стабильный числовой ID берётся из `/mid<id>/` в ссылке. Ссылка должна вести на `https://ostrovok.ru`, фото — на `https://cdn.ostrovok.ru/`. Название обрезается до 300 символов, рейтинг ограничен диапазоном 0–10, адрес читается из `streetAddress`. Дедупликация делается по ID. Верхний предел ответа — 30 карточек. Кеш на город держится 30 минут в памяти. Между стартами обращений к каталогу выдерживаются минимум 2 секунды.

Даты и число гостей валидируются, каталог общий для города. Доступность номера, стоимость на даты, свободная отмена, координаты и звёздность появляются только у источника, который реально передаёт соответствующие поля. Текущий локальный MCP возвращает название, адрес, рейтинг, фото и ссылку на карточку; фронтенд показывает ссылку и выключает фильтры цены и отмены в каталожном режиме.

### Spring, fallback и включение

`TripHotelCatalog` создаётся под флагом `ENABLE_TRIP_PLANNER`. `TRIP_HOTEL_MCP_URL` и `TRIP_HOTEL_MCP_TOOL` выбирают источник. При `CODOC_OSTROVOK_MCP_ENABLED=true` скрипт добавляет Compose-профиль `ostrovok-mcp` и задаёт значения по умолчанию `http://ostrovok-mcp:8192/mcp` и `search_hotels`. Тайм-ауты переопределяются через `TRIP_HOTEL_CONNECT_TIMEOUT` и `TRIP_HOTEL_REQUEST_TIMEOUT`. Java принимает `structuredContent.hotels` либо JSON из ограниченного текстового блока, проверяет поля и координаты, удаляет дубли и ограничивает ответ 50 карточками. При сбое закрывает клиента и делает паузу 60 секунд.

Если задан `TRIP_HOTEL_REGISTRY_FILE`, запасным источником служит локальная нормализованная выгрузка реестра до 8 МБ. Она загружается в память один раз, фильтруется по нормализованному городу и возвращается без цены и бесплатной отмены. При отсутствии пригодного источника API отдаёт состояние недоступности.

Ограничения контейнера — 64 МиБ RAM, 64 МиБ RAM+swap и 0,15 CPU. Штатный деплой собирает sidecar после образов приложения и OSM в одном ограниченном BuildKit и стартует его после остановки builder. Проверка готовности sidecar выполняется до миграций PostgreSQL.

## PoemShip

`PoemShipMcpClient` использует `HttpURLConnection` с POST и JSON-RPC 2.0. Конфигурация `APP_POETRY_POEMSHIP_URL` по умолчанию указывает на `https://poemship.com/mcp`. Клиент инициализирует сессию по первому запросу, сверяет согласованную версию протокола и посылает `notifications/initialized`. При наличии заголовка `Mcp-Session-Id` сохраняет его и использует в последующих вызовах. Идентификаторы JSON-RPC монотонно возрастают, ответ сверяется с исходным ID. Поддерживаются JSON и SSE с чтением `data:` и поиском соответствующего события. После I/O-ошибки состояние сессии сбрасывается.

Одновременно разрешён один вызов. Тайм-ауты подключения и чтения имеют верхние границы 3 и 8 секунд и дополнительно подчинены общему `PoetryFetchBudget`. Редиректы выключены. Ограничение ответа — 1 000 000 байт для JSON, для SSE проверяется суммарный размер строк в символах. Из результата принимается структурированный payload либо текст, разбираемый как JSON. Провайдер обрабатывает справочник, поиск и получение текста по правилам прикладного модуля поэзии. Остальные поэтические источники используют собственные адаптеры и бюджеты запросов.

Код: `ticket-pdf/src/main/java/ru/ticket/journey/poetry/PoemShipMcpClient.java`, `PoemShipProvider.java`, `PoemShipTextResolver.java`, `PoetryFetchBudget.java`.

## Проверки и эксплуатация

- Unit-тесты `WalkMcpClientsTest` покрывают разбор POI и контракты инструментов. `TripHotelCatalogTest` покрывает преобразование данных и fallback. Контракты PoemShip покрываются тестами модуля поэзии.
- `check-deploy-config.sh` проверяет булевы флаги. Тест `test_ostrovok_sidecar_uses_the_shared_builder_and_starts_after_it` проверяет порядок на имитаторе Docker. `check_runtime_api.py` проверяет публичные темы и дорожный пешеходный маршрут. Он не подтверждает источник фото или доступность отелей.
- Для отдельной проверки контейнера Островка нужны `GET /health`, `initialize`, `tools/list` и `tools/call` с одним поддерживаемым городом, двумя датами в допустимом диапазоне и одним числом гостей. Проверяются число карточек и `catalogOnly`. Наличие цен проверяется по реальным полям поставщика.
- Для OSM liveness нужно отдельно от проверки выборки POI. Успешный TCP healthcheck подтверждает только мост. Для Commons и PoemShip проверка доступности внешнего HTTP должна дополняться одним чтением через фактический контракт инструмента. Проверки состояния выполняются без передачи пользовательских маршрутов и без включения секретов в команды или журнал.
