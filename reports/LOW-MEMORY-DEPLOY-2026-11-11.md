# Сборка и переезд на PostgreSQL на одном сервере 2 CPU / 4 ГБ

Теперь образы по умолчанию собираются на целевом сервере. CI или другая машина не требуются. Остановка CoDoc на время сборки предусмотрена в `deploy.sh`, `build.sh`, `build.ps1`, `scripts/migrate-postgres.sh` и `scripts/deploy-postgres.sh`.

## Что изменено

- Выделенный Buildx builder `codoc-lowmem-v1`: **2304 MiB RAM**, столько же RAM+swap, квота **2 CPU**. `max-parallelism=1` запрещает одновременные тяжёлые шаги.
- Перед сборкой останавливаются только контейнеры этой установки: Java, PostgreSQL, Tyk и Redis. Чужие контейнеры не трогаются. Приложение останавливается перед базой.
- Сборка разрешается при `MemAvailable ≥ 2816 MiB`; лимиты реально созданного Docker-контейнера сверяются со значениями профиля. PowerShell читает память Docker-хоста через маленький контейнер, а не память Windows-клиента.
- Пока сборщик не остановлен, приложение не запускается. Если остановить сборщик не удалось, сервисы остаются выключенными и выводится объяснение: сборка и runtime не должны сложиться по памяти.
- Node heap — 768 MiB, Vitest — один worker. Maven heap — 384 MiB, тестовая JVM — 768 MiB, один fork. Проверки и тесты сохранены.
- Устранена фактическая причина Node OOM: ESLint создавал три TypeScript-программы при отсутствии правил, требующих типов. Правила сохранены; проверки типов выполняются отдельными процессами, включая e2e.
- В Docker-сборке отключены sourcemaps, ограничены esbuild/Node worker threads. Кеши npm/Maven и Docker-слоёв сохраняются.
- H2 копируется после остановки Java **до сборки**, с использованием старого образа. Для самой резервной копии новый образ не нужен. Исходная БД в переносе открывается read-only.
- При ошибке до изменения данных возвращаются прежние контейнеры. После начала импорта или изменения схемы старое приложение автоматически не запускается.
- Старый шлюз `codoc-gateway` возвращается с прежним Redis volume, сохраняющим ключи. Второй шлюз на том же порту не создаётся.
- `.postgres.env` публикуется после успешного переноса, а не до сборки. Повторный запуск миграции при уже созданном `.postgres.env` отклоняется.
- Обновлены инструкции для H2, PostgreSQL, новой Ubuntu-установки и Client API. Скрипты имеют LF-окончания строк, закреплённые `.gitattributes`.

## Команды на сервере

В общей папке трёх репозиториев сохранить действующий `.env` и добавить только настройки PostgreSQL, не меняя JWT, ключ шифрования и пароли действующих интеграций:

```dotenv
DATABASE_NAME=codoc
DATABASE_USER=codoc
DATABASE_PASSWORD=ваш-длинный-пароль-новой-PostgreSQL
```

Для существующей H2:

```bash
bash ticket-infra/scripts/migrate-postgres.sh --migrate
```

Для последующих обновлений PostgreSQL:

```bash
bash ticket-infra/scripts/deploy-postgres.sh
```

Обновить прежнюю H2 без переезда: `bash ticket-infra/deploy.sh`.
Только собрать образ и вернуть прежние контейнеры: `bash ticket-infra/build.sh`.

Нужны Docker Buildx, Compose v2, Bash и util-linux (`flock`). Сборка скачивает отсутствующие зависимости; первый запуск дольше последующих. Требуется свободный диск для образов, кешей и резервной копии. Не запускать параллельно `docker compose build`/`up --build`, обходящие ограниченный builder.

## Проверка

- Реальный backend `clean verify` выполнен с указанными лимитами Maven/JVM: 159 тестов, без ошибок, один ожидаемый пропуск native OCR.
- Реальные frontend-проверки и сборка выполняются с Node heap 768 MiB; полный прогон 349 unit-тестов выполнен одним worker.
- Полный браузерный набор: 68/68. Проверка покрытия пройдена: строки 89,09%, ветви 73,88%, функции 95,41%.
- 17 скриптовых тестов прошли: настоящий Bash/PowerShell и изолированный Docker double. Проверяются успех, ошибки сборки/импорта/SQL, нехватка памяти, неправильные лимиты, отказ остановки builder, восстановление старых контейнеров и сохранение чужих сервисов.
- Полный Docker-стек на физическом сервере 2 CPU / 4 ГБ в этой среде не запускался. Конкретные пики RSS и нативный Tesseract надо проверить после установки командой `bash ticket-infra/scripts/check-resource-budget.sh`.

Ограничения Buildx соответствуют [документации docker-container driver](https://docs.docker.com/build/builders/drivers/docker-container/), последовательное выполнение — [настройке BuildKit](https://docs.docker.com/build/buildkit/configure/).
