# Переход CoDoc с H2 на PostgreSQL

Скрипт останавливает запись в H2, сохраняет архив исходного тома, создаёт схему PostgreSQL текущей версией приложения и переносит данные одной транзакцией. Существующие записи целевой базы не перезаписываются. При ошибке транзакция откатывается; исходная H2 открывается только для чтения.

## Перед запуском

Для сервера **2 CPU / 4 ГБ RAM** сначала прочитайте [бюджет памяти и подготовку образов](RESOURCE-BUDGET.md).
Скрипты по умолчанию собирают образы на этом же сервере: сначала останавливают CoDoc
и сохраняют резервную копию, затем выключают остальные сервисы этой установки.
Сборка ограничена 2304 MiB / 2 CPU и выполняется последовательно. Перед запуском
PostgreSQL сборщик останавливается. Отдельный сервер сборки не нужен.
При обновлении существующей PostgreSQL скрипт после резервного копирования применяет
идемпотентные `upgrade-journeys.sql` и `upgrade-workflows.sql`, затем запускает приложение.
Первичная миграция из H2 также заполняет единый реестр адресов после переноса данных.

1. Разместите `ticket-editor`, `ticket-pdf`, `ticket-infra` рядом на сервере с Docker Compose. Сохраните действующие `JWT_SECRET`, `APP_SECRETS_ENCRYPTION_KEY`, OAuth/SMTP и прочие настройки. Смена ключа шифрования сделает сохранённые интеграции нечитаемыми.
   Скрипты миграции используют `.env` в общей папке репозиториев. Если прежняя Compose-установка хранила его в `ticket-infra/.env`, перенесите те же настройки в общую папку без генерации новых ключей. Для существующей установки не запускайте генератор новых секретов.
   Для Compose также нужны существующие `TYK_ADMIN_SECRET`, `REDIS_PASSWORD` и `APP_FRONTEND_URL`. Адрес клиентского API берётся из `CLIENT_API_PUBLIC_URL`, прежнего `APP_CLIENT_API_PUBLIC_URL` либо из `APP_FRONTEND_URL` с `/client-api`. Если шлюз ранее не устанавливался, сначала настройте его по документации Client API; не заменяйте уже используемые секреты вновь сгенерированными.
2. В существующий `.env` добавьте:

```dotenv
DATABASE_NAME=codoc
DATABASE_USER=codoc
DATABASE_PASSWORD=replace-with-a-long-random-password
DB_SCHEMA_MODE=validate
```

3. Выделите время остановки сервиса. Проверьте свободное место для H2-архива, новой PostgreSQL и дампа. PostgreSQL не публикуется в интернет.
4. Если файл H2 в `/app/data` называется иначе, задайте `H2_FILE_NAME`, например `documents.mv.db`: это имя проверяется до резервного копирования и используется для read-only URL мигратора. Для особого URL доступен `H2_MIGRATION_URL`; обязательны `IFEXISTS=TRUE;ACCESS_MODE_DATA=r;FILE_LOCK=NO`. Для зашифрованной H2 укажите её настройки отдельно.

## Запуск

Из родительской папки репозиториев:

```bash
bash ticket-infra/scripts/migrate-postgres.sh --migrate
```

Не запускайте скрипт повторно поверх заполненной PostgreSQL: он остановится, а данные останутся нетронутыми. Он сверяет количество перенесённых строк каждой таблицы. Проверьте дополнительно вход, документы, схемы, наборы данных, генерацию PDF, историю и сохранённые интеграции. Таблицы новых функций могут быть пустыми — это ожидаемо.

Скрипт также распознаёт старый контейнер `ticket-app` с bind-каталогом. Он сохраняет этот каталог и порт 8080, останавливает старый контейнер и записывает параметры в `.postgres.env`. Не удаляйте этот файл. Для исходного Compose-развёртывания сохраняется порт 8090.

Существующий шлюз из проекта `codoc-gateway` и его Redis останавливаются на время сборки,
а затем запускаются с прежними volumes и ключами. Новое приложение подключается также
к сети `codoc-client-api` под прежним именем `app`. Второй шлюз поверх старого не создаётся.

После миграции используйте обёртку:

```bash
./ticket-infra/deploy.sh
```

Для ручных команд экспортируйте `.postgres.env` и используйте **оба** файла:

```bash
set -a; source .env; source .postgres.env; set +a
docker compose --env-file .env -f ticket-infra/compose.api.yml -f ticket-infra/compose.postgres.yml logs --tail 100 app
./ticket-infra/deploy.sh
```

## Откат

До приёма новых записей в PostgreSQL можно остановить приложение и вернуть сохранённый старый образ с исходным H2-томом:

```bash
docker compose --env-file .env -f ticket-infra/compose.api.yml -f ticket-infra/compose.postgres.yml stop app
docker compose --env-file .env -f ticket-infra/compose.api.yml -f backups/postgres-ВРЕМЯ/rollback.yml up -d --no-build app
```

Если исходным был контейнер `ticket-app`, вместо запуска Compose-отката можно после остановки нового приложения выполнить `docker start ticket-app`: старый контейнер сохраняется. Убедитесь, что порт 8080 свободен.

После появления новых данных в PostgreSQL такой откат потеряет их из пользовательского представления: сначала нужен отдельный согласованный перенос изменений. Архив H2 и дамп PostgreSQL сохраняйте вне сервера. Не удаляйте исходный том и не используйте `docker compose down -v`.

## Детали

`ticket-pdf/tools/H2ToPostgres.java` использует JDBC и драйверы из собранного приложения. JSON переносится как JSON, CLOB — как текст. Целевые таблицы блокируются, зависимости между таблицами учитываются, ошибки прерывают всю транзакцию. Отсутствующая таблица или колонка требует проверки схемы, а не игнорируется.

Официальные справочники: [резервное копирование H2](https://h2database.github.io/html/commands.html), [перенос явных значений identity в PostgreSQL](https://www.postgresql.org/docs/17/sql-insert.html).
